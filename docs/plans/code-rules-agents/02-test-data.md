# Агент 2 — тестовые данные и фикстуры

Работай в репозитории `/Users/zenalark/PycharmProjects/Test-java/getting-started-python`.
Прочитай актуальный `AGENTS.md`, `docs/plans/code-rules-compliance.md`
и относящиеся к задаче разделы `knowledge/components/`.

Это задача на реализацию указанной фазы. Проверь фактическое состояние кода:
предыдущие агенты могли изменить пути и количество тестов. Сохраняй существующие
незакоммиченные изменения. Не ослабляй правила проекта и проверки тестов.
При переносе компонента обновляй всех потребителей, документацию и запись
каталога в том же изменении. Не выводи секреты и не отправляй Telegram-сообщения.
Не создавай коммиты, не публикуй изменения и не запускай CI без отдельного запроса.

Предусловие: фаза 1 завершена и её изменения доступны в рабочем дереве.
Проверь результат предыдущего агента перед изменением импортов.

Задача — выполнить фазу 2 плана:

1. Вынеси фиксированные входные и ожидаемые данные UI-тестов
   в тематические модули `test_data/consts/`: сообщения, заголовок,
   заведомо неверный пароль и суффикс несовпадающего пароля.
2. Отдельно вынеси входные и ожидаемые данные unit-тестов.
   Значение, используемое как тестовый пример технической настройки,
   является тестовыми данными; саму настройку инфраструктуры переносить
   в тестовые константы не нужно.
3. Вынеси параметры генерации данных: префикс имени, длины имени и пароля.
   Используй содержательные имена `UPPER_SNAKE_CASE` и явные импорты.
4. Не переноси в тестовые константы локаторы, тексты Allure-шагов,
   имена переменных окружения и технические настройки компонентов.
5. Для изменяемых наборов обеспечь отдельные экземпляры на каждый тест.
   Проверь, что вложенные изменяемые структуры также не разделяются.
6. Сохрани уникальные данные `new_user` на каждый тест и использование
   `existing_user` без изменения общего аккаунта.
7. Проверь документированные и доступные механизмы удаления созданных
   пользователей. Если удаление доступно — реализуй teardown в фикстуре,
   которая владеет созданной сущностью. Не удаляй существующий общий аккаунт
   и не делай teardown для сущности, которую тест не создал.
   Если механизм отсутствует или доступность проверить невозможно,
   зафиксируй это ограничение без выдуманного API или ложного вывода.
8. Обнови затронутые разделы каталога и примеры.

Граница задачи: тестовые данные и их жизненный цикл; сохраняй сценарии
и результаты проверок. Массовую Allure-разметку оставь следующему агенту.

Проверки:
- `.venv/bin/python -m pytest tests/unit -q -p no:cacheprovider`
- `.venv/bin/python -m pytest --collect-only -q -p no:cacheprovider`
- `git diff --check`
- Проверь повторное использование данных на отсутствие общей мутации.

Критерии готовности: фиксированные данные вынесены, генераторы остаются
уникальными, исходные тесты собираются, unit-тесты проходят, возможности
и ограничения очистки явно описаны.

Заверши работу отчётом: изменённые файлы, результат по каждому критерию,
команды и результаты проверок, ограничения и оставшиеся задачи для следующего
агента. Обнови статус своей фазы в `docs/plans/code-rules-compliance.md`;
не отмечай невыполненные или заблокированные проверки как успешные.
